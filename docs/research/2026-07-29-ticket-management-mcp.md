# Ticket Management for TicketLens's MCP Server — Research & Proposal

**Status:** Research complete. Not planned/approved for implementation. Resolves the "unscoped" state of [[project_ticket_crud_backlog_2026_07_27]] with a concrete, evidence-based proposal — scope still needs explicit user approval before any code is written.

**Origin:** User's own daily-workflow request (2026-07-27), reopening a 2026-03-12 rejection ("market saturated, dilutes read-side-intelligence positioning, recommend jira-cli instead"). Revisited now specifically in light of the shipped MCP server (`ticketlens mcp`, v0.22.0/v0.23.0) — the question isn't just "should TicketLens do ticket CRUD" anymore, it's "should ticket actions be exposed as MCP tools."

## 10-iteration research loop (scored, web-verified)

1. **4/10** — naive brainstorm: every CRUD verb (create, read, update, delete, assign, link, comment, transition, watch, label, attach). Unfiltered, no competitive check.
2. **6/10** — checked the real competitive bar. **jira-cli** (ankitpokhrel, 5.1K★, free OSS): create, multi-field edit, transition/move+comment, assign — mature, comprehensive, years of edge-case handling. **Atlassian's own official MCP server** (Rovo, GA Feb 2026, hosted at `mcp.atlassian.com`): 16 Jira tools — JQL search, read issues/metadata, create issues, edit fields, transition status, add comments, log work, bulk create/update. Critically: **no delete-issue tool** (and no delete-page tool for Confluence either) — explicitly documented as "a sensible blast-radius decision" by Atlassian itself. Strongest single piece of evidence in the whole research — the best-resourced possible competitor deliberately excludes delete.
3. **6.8/10** — re-examined TicketLens's actual wedge against that competitor: tracker-agnostic (Jira Server/DC + GitHub Issues + Linear, via adapters already built in this codebase) vs. Atlassian's Jira/Confluence/Bitbucket/Compass-only, **cloud-only** MCP (per existing `project_competitive.md`: "No Jira Server or Data Center support (cloud-only OAuth)"). A uniform ticket-action interface across trackers is something Atlassian's own tool structurally cannot be. That's the real differentiation — not feature-parity catch-up on Jira Cloud specifically.
4. **7.3/10** — tie actions to TicketLens's existing intelligence instead of shipping generic CRUD: a transition tool that runs the existing compliance check before allowing a move to Done/Resolved; an assign tool informed by existing collision-detection data. Directly answers the original rejection's "no habit loop, doesn't compound with existing value" concern.
5. **7.8/10** — ordered by the original rejection's strongest technical worry ("custom fields, workflow transitions, screen schemes = months of edge-case debugging"). Comment and transition (via each tracker's own transition/state metadata, never hardcoded workflow assumptions) are the lowest-complexity, lowest-risk actions. Arbitrary custom-field creation is the highest-complexity, highest-risk end. Proposed MVP order: **comment → transition** → assign → link → create (fixed minimal fields) → update (narrow named-field set only). Delete and arbitrary custom fields explicitly excluded from MVP.
6. **8.2/10** — tier fit: gate behind Pro+ (parallel to Recall/compliance), not Free. This is an "act," not "read faster" lever — addresses the original "weak conversion lever" concern directly.
7. **8.5/10** — MCP tool-design shape: separate granular tools (`ticket_comment`, `ticket_transition`, `ticket_assign`, `ticket_link`, `ticket_create`, `ticket_update`) rather than one dispatcher tool — matches Atlassian's own 16-discrete-tools precedent, keeps per-action tier-gating/audit-logging clean.
8. **8.8/10** — write actions hit a *live customer system*, categorically different from Phase 1's local-only Recall vault. Needs confirmation/`--dry-run` semantics by default (same convention already established by `note add`/`mcp install`), clear audit logging (ties into the already-shipped `AuditService`), and explicit rate-limit awareness — the Atlassian research itself flagged bulk writes burning through Jira's points-based quota fast.
9. **9.1/10** — security bar is higher than Phase 1's Recall tools precisely because of that last point: a tool that can mutate a customer's real tickets is a materially more attractive target for a poisoned/malicious instruction (2026 MCP tool-poisoning landscape, researched in Phase 1). Needs narrow, named parameter schemas per tool — never a raw-payload passthrough an AI could use to smuggle unintended field changes — and likely a Team-manager-configurable allowlist of which actions are even enabled, mirroring the existing Console permission-bit pattern.
10. **9.4/10 — STOP (cap reached).** Held short of 10 honestly: writing to a live external system is a higher, not fully eliminable risk class than Phase 1's local vault. Real production hardening (per-tracker adapter testing, rate-limit handling, confirmation UX) is still required before "planned" becomes "done."

## Existing codebase grounding (read directly, not assumed)

All three tracker adapters (`skills/jtb/scripts/lib/adapters/{jira,github,linear}-adapter.mjs`) are **100% read-only today** — each `createXAdapter(conn)` returns an object with only `fetchTicket`/`fetchCurrentUser`/`searchTickets`/`fetchStatuses` (Jira also has these; GitHub/Linear implement the same shape independently). No write methods exist anywhere in any adapter. Comment/transition would be genuinely new adapter surface, not an extension of something partial.

## Real per-tracker mechanics (web-verified, not assumed)

- **Jira:** `GET /issue/{key}/transitions` (discover valid transition IDs — never hardcode workflow names) → `POST /issue/{key}/transitions` with the chosen `transition.id`. Comments: `POST /issue/{key}/comment`. API v3 (Cloud) supports ADF-formatted comment bodies; v2 (Server/DC) does not — this adapter already branches on `apiVersion` for reads, same branch point applies to writes.
- **GitHub:** Comments: `POST /repos/{owner}/{repo}/issues/{issue_number}/comments`. State change: `PATCH /repos/{owner}/{repo}/issues/{issue_number}` with `state: "open"|"closed"`. GitHub Issues has no Jira-style multi-step workflow — only open/closed — so `ticket_transition` on a GitHub-backed ticket is necessarily a much smaller state space than on Jira.
- **Linear:** GraphQL mutations. Comments: `commentCreate(input: { issueId, body })`. State change: `issueUpdate(id, input: { stateId })` — requires first querying the team's available `WorkflowState`s to resolve a human-meaningful status name (e.g. "In Progress") to its `stateId`, same two-step shape as Jira's transition-ID discovery.

Sources: [Atlassian Jira Cloud REST API v3](https://developer.atlassian.com/cloud/jira/platform/rest/v3/) · [jira-cli (ankitpokhrel)](https://github.com/ankitpokhrel/jira-cli) · [Atlassian Rovo MCP server coverage](https://www.usecarly.com/blog/jira-mcp/) · [MCP write-operations limitations discussion](https://community.atlassian.com/forums/Jira-questions/MCP-Server-Integration-Limited-Write-Operations-for-Jira-Issues/qaq-p/3113619) · [GitHub REST API — issue comments](https://docs.github.com/en/rest/issues/comments) · [GitHub REST API — issues](https://docs.github.com/en/rest/issues) · [Linear GraphQL API](https://linear.app/developers/graphql)

### Resulting design (pending the two open unknowns above)

- New adapter methods on all three (`jira-adapter.mjs`/`github-adapter.mjs`/`linear-adapter.mjs`): `addComment(key, body, opts)`, `transition(key, target, opts)` — `transition` without a resolved target/`confirm` returns the tracker's valid options for that ticket instead of executing (Jira: `GET /issue/{key}/transitions`; Linear: query `WorkflowState`s for the team; GitHub: static `["open","closed"]`).
- New CLI subcommands `ticketlens comment`/`ticketlens transition`, human-usable standalone (matches the user's own daily-workflow origin), following the existing adapter-dispatch pattern via `resolve-adapter.mjs`.
- MCP tools `recall`-style thin wrappers: `ticket_comment`, `ticket_transition` — zero reimplementation, same pattern as `recall_add`/`recall_search` over `note add`/`recall`.
- `confirm: true` two-step gate on `ticket_transition` — explicit in the tool description as "requires confirmation," framed honestly as a nudge + audit trail, not a security boundary.
- Pro+ gate on both, consistent with the whole Recall/MCP family.
- Rate-limit-aware error handling per adapter, distinguishing "rate limited, retry after Xs" from a generic failure — mirrors the existing pattern already proven in `recall-sync.mjs`.
- Compliance-check integration explicitly deferred, opt-in only if ever built — never bundled silently into `ticket_transition`.

## Approved plan — Pre-Code Audit amendments (2026-07-29)

Plan approved. 3 parallel audit lenses found real design issues before any code was written — folded in here, "cleared with amendments":

- **[Security, highest priority] New Jira write calls must live in `jira-client.mjs`, not `jira-adapter.mjs`.** `jira-client.mjs` owns `guardedFetch` (DNS-rebind guard, SSRF blocklist, manual-redirect-only, HTTPS-enforced). A write method built directly in the thin adapter file with a raw `fetch()` would silently lose that protection entirely. `addComment`/`transition` go in `jira-client.mjs` (calling `validateBaseUrl` + `guardedFetch`, same as the 4 existing read exports), thinly re-exported from `jira-adapter.mjs`.
- **[Security, highest priority] `mcp-server.mjs` must never import adapters directly.** Confirmed today: `callRecallAdd`/`callRecallSearch` only ever call the already-gated CLI functions (`runNoteAddFn`/`runRecallFn`), never touch an adapter. New `runTicketCommentFn`/`runTicketTransitionFn` must be wired the identical way — the Pro+ gate lives in `ticket-command.mjs`, and the MCP layer calling straight into an adapter would fully bypass it.
- **[Security] Audit log entries must be JSON-serialized per line, never plain-text-concatenated.** Comment bodies are attacker/AI-controlled free text — an embedded newline could forge fake log lines otherwise (same bug class already fixed once in this codebase, `feedback_brief_section_filename_escaping`). Ticket keys must pass `TICKET_KEY_PATTERN` before touching any file path or log line.
- **[Performance/data-safety] Split cooldown-state and audit log into two separate files**, not one. A single growing log serving both roles degrades the cooldown check from O(1) to O(n) (scanning full history per invocation), or risks one read-modify-write clobbering the other's data. `ticket-action-cooldown.mjs` (small JSON map, `{key:action -> lastAt}`, same read pattern as `recall-queue.mjs`) separate from `ticket-action-log.mjs` (append-only).
- **[Seniority] Split `transition` into two exported CLI-layer functions from the start**: `runTicketTransitionList` (discovery, read-only) and `runTicketTransition` (execute, requires a resolved target + confirm) — each independently matching the established `runX(cmdArgs, deps) -> {ok}` single-decision shape, dispatched from the same `ticketlens transition` subcommand based on whether a target/confirm was given, rather than one function branching internally like two commands.
- **[Seniority] Explicit `classifyWriteFailure`-style helper in `ticket-command.mjs`** distinguishing retryable/terminal/rate-limited errors for both CLI and MCP callers — mirrors `recall-queue.mjs`'s `isRetryableFailure`/`pushNote` pairing rather than falling through to a generic catch that loses the distinction.
- **[Performance/safety] No automatic retry on write timeout.** A timed-out write may have actually landed server-side — unlike Recall's notes (idempotent by `external_id`, safe to retry), ticket comments/transitions are not naturally idempotent. Explicit rule: never auto-retry a timed-out write.
- **[Performance] No in-process transition-discovery caching.** No memoization layer exists anywhere in `lib/` today, and each CLI invocation is a fresh process — a cache would have zero payoff now. Explicitly not building it; note for a future batch-mode if one is ever added.

## Remaining scope — `ticket_link`, `ticket_create`, `ticket_update`, duplicate-ticket detection (2026-07-29, second pass)

10-iteration scored/refuted loop, real websearch verification at every uncertain point (sources per finding below — not inferred from the first pass's research, freshly confirmed).

1. **4/10 — naive:** ship all four as one large PR. Refuted immediately — breaks the pattern that worked three times running (comment/transition/assign each shipped as an independently-reviewable slice); `ticket_create` is architecturally unlike the other three (no existing ticket key to operate on) and duplicate-detection is pure read, zero write risk — bundling them erases real risk differences that should drive review depth and sequencing.
2. **6/10 — sequence by the original doc's listed order** (link → create → update, duplicates separate). Refuted — that order was a guess made before any of this pass's research; real risk/dependency data below contradicts it.
3. **7/10 — real finding, `ticket_link` (Jira):** `POST /rest/api/3/issueLink` — `{type:{name:"Duplicate"}, inwardIssue:{key}, outwardIssue:{key}}`, no response body on success (same 204-style pattern as transition/assign). **[Atlassian Cloud API v3 issue-links](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-links/)**. Refuted my own draft: the link-type **name** ("Duplicate", "Blocks", "Relates") is Jira-instance-configurable, not a fixed universal string — hardcoding it risks a 400 on any instance that renamed/customized link types. Must discover via `GET /issueLinkType` first (same "list-then-act" shape as transition discovery), never assume the name.
4. **7.4/10 — real finding, `ticket_link` (GitHub):** GitHub's native "close as duplicate" (REST, added late 2024) is `PATCH /issues/{n}` with `state:"closed"`, `state_reason:"duplicate"`, **plus a dedicated `duplicate_issue_id` parameter** — confirmed via direct doc fetch: *"The ID of the issue to mark as the canonical duplicate when state_reason is duplicate... Ignored when state_reason is not duplicate."* **[GitHub REST — Update an issue](https://docs.github.com/en/rest/issues/issues?apiVersion=2022-11-28#update-an-issue)**. Refuted my own assumption that this is a simple flag — it's a real link action, not just a close reason. **Genuinely unconfirmed, flagged not guessed:** whether `duplicate_issue_id` wants the issue's internal `id` (globally unique) or its repo-local `number` (the visible `#42`) — GitHub's own `_id`-suffix convention (e.g. `milestone.id` vs `milestone.number`) suggests internal `id`, but no source directly confirms it. Compounding gap: `normalizeGitHubIssue` in this codebase currently exposes only `raw.number`, never `raw.id` — so GitHub's `ticket_link` would need either a live API test against a real repo to confirm which field, or an explicit "additive field" change to `normalizeGitHubIssue`/`fetchTicket` mirroring the `assign` feature's `login`/`id` pattern, decided only after that's confirmed. Also: GitHub's mechanism is a "duplicate, closing" action, structurally different from Jira/Linear's "just link, don't change state" — the tool's semantics need to account for this platform asymmetry rather than pretend all three trackers behave the same.
5. **7.9/10 — real finding, `ticket_link` (Linear):** `issueRelationCreate` mutation exists, operating on `issueId`+`relatedIssueId`+a `type` accepting values described as "blocks"/"duplicate"/"related" **[Linear GraphQL schema, Apollo Studio](https://studio.apollographql.com/public/Linear-API/variant/current/schema/reference/objects)**. **Genuinely unconfirmed:** exact enum casing/name (`IssueRelationType.duplicate` vs `.DUPLICATE` vs a different literal) — not resolved by search, needs direct GraphQL introspection (`{ __type(name: "IssueRelationType") { enumValues { name } } }`) at implementation time, not guessed now.
6. **8.1/10 — real finding, `ticket_create` required fields (Jira):** `project` (id or key), `issuetype`, `summary` are the confirmed minimum; `description` on Cloud (v3) needs ADF — **directly reuses the existing `textToAdf()` from the comment feature**, a genuine synergy, not new code **[Atlassian Cloud — create issue](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/)**. Refuted the original doc's implicit assumption that "type" can be a hardcoded default (e.g. "Task") — issue types are project-configurable; a hardcoded default risks a 400 on a project without that type name. Resolution mirrors transition's existing 400-detail-surfacing pattern (`err.details`) rather than pre-validating via a second discovery call — simpler, and Jira's own error message already names the problem field.
7. **8.4/10 — real finding, `ticket_update` (Linear):** `IssueUpdateInput` confirmed to include `title`, `description`, `priority` (an **integer 0–4**, not a string enum — 0=none,1=urgent,2=high,3=normal,4=low), `labelIds` (**wholesale replace**), and separately `addedLabelIds`/`removedLabelIds` (**incremental**) **[Linear API field reference, via WithOne AI knowledge base cross-checked against Linear's own docs pattern](https://www.withone.ai/knowledge/linear/conn_mod_def::GJ4vKPA5pxw::aWslYh49RQKh7negDKtW2w)**. Refuted my own draft design (a single `--labels=X,Y` replace-only flag) — replacing wholesale by default is a real data-loss risk (silently drops every label a teammate already added); `ticket_update`'s label handling should default to **add/remove**, matching the "narrow, safe, named field set" philosophy already established for this whole feature family, with a wholesale replace only as an explicit opt-in if ever needed.
8. **8.7/10 — real finding, `ticket_update` (Jira) — this changes the whole design:** Jira's update API does **not** work like a simple field-replace PUT at all. Multi-value fields use a **verb-based operation array**: `{"update": {"labels": [{"add": "X"}, {"remove": "Y"}]}}` — SET/ADD/REMOVE are distinct verbs per field **[Atlassian Server — updating an issue](https://developer.atlassian.com/server/jira/platform/updating-an-issue-via-the-jira-rest-apis-6848604/)**. This is a **different shape from both GitHub (plain `PATCH {labels:[...]}`, full-replace, confirmed by existing pattern in this codebase's `github-adapter.mjs` reads) and Linear (named `labelIds` vs `addedLabelIds`/`removedLabelIds` fields)** — three genuinely different label-update mechanics across three trackers, not one shape with three transports. Refuted my own iteration-7 assumption that a single internal `{add:[], remove:[]}` representation could map uniformly onto all three — it can, but each adapter's translation layer is nontrivial and needs its own dedicated tests, not a shared helper that assumes structural similarity.
9. **9/10 — sequencing conclusion, refuted and re-decided:** Given real risk (not just the doc's original listed order): **duplicate-ticket detection first** — it is the ONLY one of the four with zero write risk (pure read: search + local Jaccard-similarity scoring, same zero-deps approach already scoped in the paused-and-resumed earlier session), it's the single item the user has now asked about twice, and per-tracker candidate-search groundwork it needs (Jira JQL text search reusing existing `searchTickets`, GitHub `GET /search/issues`, Linear `searchIssues`) doesn't block on any of the three genuinely-unconfirmed API details above. **`ticket_link` second** — real risk is low (adding/removing a relationship is reversible), but needs the Jira link-type-discovery call and the GitHub `duplicate_issue_id` field-identity question resolved with a live test before implementation, not guessed. **`ticket_update` third** — three genuinely different per-tracker mechanics now confirmed, more implementation surface than link, but each write is narrow/reversible (a title/label/priority change, not new-state creation). **`ticket_create` last** — the only one of the four that fabricates a brand-new tracked work item in a real system; highest blast radius if project/issuetype resolution goes wrong (a bogus ticket in a real Jira/GitHub/Linear project is harder to walk back cleanly than a bad comment or label), and it depends on nothing the other three need first.
10. **9.4/10 — STOP, final:** Sequencing above is a *recommendation*, not a decision I'm entitled to make alone — the user asked for all four planned, not necessarily built in this exact order, and duplicate-detection specifically was something the user raised unprompted twice. Three genuine open unknowns remain, honestly unresolved by search (not modesty — real gaps): (a) GitHub `duplicate_issue_id` — internal `id` vs `number`, needs a live API check; (b) Linear's `IssueRelationType` enum exact literal, needs a live schema introspection query; (c) whether Jira's `GET /issueLinkType` should run per-connection-setup (cached) or per-call (fresh) — a design choice, not a research gap, deferred to implementation.

## `ticket_link` — 10-iteration refute loop (2026-07-29, third pass)

Both previously-flagged open unknowns resolved this pass via primary sources, not guessed:

- **GitHub `duplicate_issue_id`:** confirmed via direct quote from [GitHub REST docs — Update an issue](https://docs.github.com/en/rest/issues/issues?apiVersion=2022-11-28#update-an-issue): type `integer`, *"The ID of the issue to mark as the canonical duplicate... The issue must exist and be accessible to the authenticated user."* This is the issue's internal `id` (int64), **not** its repo-local `number`. Confirms the real codebase gap already flagged: `github-adapter.mjs`'s `normalizeGitHubIssue` (line 29-53) exposes only `raw.number` (via `key`), never `raw.id` — must be added.
- **Linear `IssueRelationType` enum casing:** confirmed via Linear's own GraphQL-codegen-generated TypeScript types (`evangodon/linear-cli`, a real open-source Linear CLI whose types are generated directly from Linear's schema via introspection — not hand-written, not guessed): `enum IssueRelationType { Blocks = 'blocks', Duplicate = 'duplicate', Related = 'related' }` — lowercase string values. Same source also confirms the mutation input shape: `IssueRelationCreateInput { id?, issueId: String!, relatedIssueId: String!, type: IssueRelationType! }`, and `IssueRelationPayload { issueRelation, lastSyncId, success: Boolean! }` — same `success` check pattern already used by `assignToSelf`.
- **Jira `issueLinkType`/`issueLink` shapes:** confirmed via WebSearch — `GET /rest/api/3/issueLinkType` returns `{ issueLinkTypes: [{id, name, inward, outward, self}] }`; `POST /rest/api/3/issueLink` body `{type:{name}, inwardIssue:{key}, outwardIssue:{key}}`, returns **204 No Content** on success (same pattern as transition/assign).

1. **5/10 — naive:** one `linkTo(sourceKey, targetKey, type)` adapter method, uniform across all three trackers. Refuted immediately — GitHub has no generic link primitive at all; its only real "link" action is closing the source issue as a duplicate of the target (`state_reason:"duplicate"` + `duplicate_issue_id`), which is asymmetric (mutates the *source's state*, not just a relationship) and only supports one relation type ("duplicate"). A uniform method signature would hide this real asymmetry from callers.
2. **6/10 — real finding, direction semantics:** Jira's `inwardIssue`/`outwardIssue` are directional — `{name:"Duplicate", inward:"Duplicated by", outward:"Duplicates"}` means *outwardIssue* "Duplicates" *inwardIssue*. Linear's `issueId`/`relatedIssueId` are also directional per the confirmed input shape (`issueId` is the subject of `type`). Refuted the assumption that "link A and B" is symmetric — it isn't, for either tracker with a real "duplicate" semantic. Convention adopted: `ticketlens link SOURCE TARGET --type=X` means *SOURCE* `type`s *TARGET* (SOURCE→outwardIssue/issueId, TARGET→inwardIssue/relatedIssueId) — must be stated explicitly and prominently in help text since it's genuinely non-obvious and easy to get backwards.
3. **6.8/10 — real finding, GitHub scope:** GitHub only supports "duplicate" as a link type, and only by closing the source. If a user asks for `--type=Blocks` on a GitHub-tracked ticket, the command must say so explicitly ("GitHub only supports linking as a duplicate — no generic link types") rather than silently no-op or send a malformed request.
4. **7.5/10 — two-step "list-then-act" shape, mirroring `transition`:** `ticketlens link SOURCE TARGET` (no `--type`) lists available options — for Jira, a **live** `GET /issueLinkType` call (per-instance customizable, so must be fresh, never hardcoded/cached — same "never trust a stale list" principle as `getTransitions`); for GitHub/Linear, a **static** printed list (their type sets are fixed by the platform, not per-instance-configurable, so no network call is needed or honest to imply). `--type=X --confirm` executes.
5. **8/10 — real finding, GitHub id gap confirmed via code read:** `github-adapter.mjs`'s `normalizeGitHubIssue` must gain an `id: raw.id` field (additive, non-breaking) so `findCandidates`... no — so `link` can resolve the target's internal id via the existing `fetchTicket(targetKey)` call, mirroring the exact "silently dropped field" pattern already found and fixed for `fetchCurrentUser` during the `assign` build (`login`/`id`).
6. **8.3/10 — real finding, cross-tracker/cross-profile guard:** GitHub's own docs say the target issue "must exist and be accessible to the authenticated user" — it does NOT require the same repo. Without an explicit guard, a caller could accidentally link across repos if two profiles happen to share a token. Design decision: resolve both SOURCE and TARGET through the **same adapter instance** (derived from SOURCE's profile) — TARGET is fetched via that one adapter's `fetchTicket`, never a second `resolveTicketAdapter` call — so cross-profile linking is structurally impossible, not just discouraged.
7. **8.6/10 — real finding, both keys need validation:** every prior write command (comment/transition/assign) validates exactly one ticket key via `requireTicketKey`/`TICKET_KEY_PATTERN`. `link` is the first feature needing **two** independently-validated keys (source and target) — a real, new requirement on `ticket-command.mjs`, not reducible to the existing single-key helper as-is. Needs a second validation call (or a small extension) before either key reaches an adapter.
8. **9/10 — cooldown/audit key shape, refined after reading both modules directly:** `ticket-action-cooldown.mjs`'s `checkCooldown`/`recordAction` accept arbitrary strings with no validation — safe to pass a composite key (`${sourceKey}:${targetKey}` as the "ticketKey" param, `'link'` as action) so a second link to a *different* target isn't blocked by the debounce window. But `ticket-action-log.mjs`'s `logAction` **strictly validates** `ticketKey` against `TICKET_KEY_PATTERN` and throws on anything else (confirmed by reading the file — this isn't a guess) — a composite key would break every successful link's audit-log write. Resolution: cooldown keys on the pair (composite string, no code change needed — `checkCooldown`/`recordAction` are already string-agnostic); the audit log keeps `ticketKey: sourceKey` (a real, valid single key) and records `detail: { targetKey, type }` — same shape convention as `assign`'s `detail: { assignee }`. No change needed to either existing module.
9. **9.3/10 — refuted my own iteration-4 assumption:** I assumed GitHub/Linear's "static list" could just be a hardcoded array printed with no adapter call at all — true for Linear (`blocks`/`duplicate`/`related` are schema constants), but for GitHub the "list" isn't really a list of types (there's only one: duplicate) — so GitHub's list-mode should say plainly "GitHub only supports: duplicate" rather than pretend-list a single-item array like Jira's real multi-item list. Cosmetic but avoids a misleading uniform UI across trackers that fundamentally differ here.
10. **9.5/10 — STOP, final design:**

- **[HIGH]** `getLinkTypes()` had a split contract — Jira returned `{id,name,inward,outward}` objects while GitHub/Linear returned plain strings, and `runTicketLinkList` rendered whichever it got with a bare `${t}` template literal. - **[HIGH]** Neither Jira's nor Linear's `linkTo` validated the caller's `--type` against a fresh list before mutating (unlike `transition`'s established "look-then-act" idiom). - **[MEDIUM]** `runTicketLink` discarded `linkTo`'s return value entirely — would have silently reported success on a `{executed:false}` result once the fix above landed. Now checks `result.executed`.

## `ticket_update` — 7-iteration proposal/critique loop (2026-07-30, fourth pass)

Two corrections to this doc's own earlier findings, confirmed via direct WebFetch/WebSearch on primary sources rather than reused from the first pass:

- **GitHub labels are NOT plain-PATCH-full-replace, contrary to iteration 8 above.** GitHub has dedicated atomic endpoints: `POST /issues/{n}/labels` (additive) and `DELETE /issues/{n}/labels/{name}` (single removal) — confirmed via direct WebFetch on GitHub's labels docs. Using the full-replace `PATCH`/`PUT` would have forced an unsafe read-then-write race; the real API avoids it entirely. A 404 on removal means the label was already absent — treated as idempotent success, not a failure.
- **Linear's `addedLabelIds`/`removedLabelIds` (`IssueUpdateInput`, shipped Jan 2025) take real label UUIDs, never names, and do not auto-create a missing label** — confirmed via WebSearch. A name must resolve against a fresh, team-scoped `issueLabels` query first (same shape as the existing `fetchTeamWorkflowStates` helper); an unresolvable name reports `not-found` rather than reaching `gql()` raw (which would misclassify it as a network/timeout error, the same bug class already fixed once for `linkTo`).
- **The real rule governing `--confirm` across this whole feature family, resolved by reading `runTicketComment`/`runTicketAssign` directly:** it gates the boundary between a discovery step and an execution step (`transition`/`link` both have list-then-act shapes). `comment`/`assign` have no discovery step and ship with no `--confirm`. `ticket_update` has no discovery step either (priority validity surfaces the tracker's own error, same choice already made for `ticket_create`'s issuetype) and its edits are reversible metadata changes with no workflow-state side effects — same risk tier as `assign`, not `transition`/`link`. Decision: no `--confirm` flag.
- GitHub Issues have no native priority field at all (confirmed by the codebase itself — `normalizeGitHubIssue` always sets `priority: null`) — `ticket-command.mjs` refuses `--priority` on a GitHub-tracked ticket before the adapter is ever called, mirroring `ticket_link`'s GitHub-type-mismatch guard.

### Resulting design

| Concern | Jira | GitHub | Linear |
|---|---|---|---|
| Title/description | `PUT /issue/{key}` `fields:{summary, description}` (description via existing `textToAdf()` on v3) | `PATCH /issues/{n}` `{title, body}` | `issueUpdate` `{title, description}` |
| Priority | Same PUT, `fields:{priority:{name}}` — invalid name surfaces Jira's own 400 | Refused before the adapter is called — no native field | `issueUpdate` `{priority: int}` — string name reverse-mapped via existing `PRIORITY_LABELS`; unresolvable name → `not-found`, no network call |
| Labels | Same PUT, `update:{labels:[{add}/{remove}]}` — freeform strings, Jira auto-creates on add | `POST .../labels` (add, batched) + `DELETE .../labels/{name}` per removal (404 = already-absent = success) | Resolve names→IDs via team-scoped `issueLabels` query first, then `addedLabelIds`/`removedLabelIds` in the same `issueUpdate` call |
| Atomicity | All 4 sub-fields in one HTTP call | Title/desc atomic; each label op independent — genuine partial-failure surface | Label resolution (read) + one atomic mutation |
| Result shape | Throws on failure (single atomic call, same as every other write) | Always returns `{ applied, errors }` — best-effort, continues after a failure | Pre-flight resolution errors are non-throwing; the mutation itself throws on failure like Jira |

**Shipped as `ticketlens update` / `ticket_update` (v0.28.0).** Code review: 0 CRITICAL, 0 HIGH (2 LOW accepted: comma-in-label-name edge case matching the existing `note add --tags` precedent; duplicate error text when GitHub's shared title/description PATCH fails). Next up per the risk-based order: `ticket_create` last — the only one of the four that fabricates a brand-new tracked item in a real system.

## File/image attachments on `ticket_create`/`ticket_comment` — shipped (2026-08-01)

10-iteration research loop run before any code, web-verified at every uncertain point, followed by real live-instance experimentation that overturned one of the loop's own conclusions (detail below). New modules: `attachment-uploader.mjs` (shared local-file validation — 10MB/file, 50MB/call aggregate, 20-file count caps, all checked via `stat` before any `readFileSync`), `jira-attachment-client.mjs` (`uploadAttachment` — multipart via native `FormData`/`Blob`, `X-Atlassian-Token: no-check`, reusing `guardedFetch`/`validateBaseUrl`/`buildAuthHeader` unmodified; `resolveMediaId` — see below). `adf-converter.mjs` gained `buildMediaNode`/`appendNodesToAdf`. `jira-client.mjs`'s `postComment` gained an `extraAdfNodes` opt (Cloud-only, backward-compatible default `[]`).

**Per-tracker outcome, all three real:**
- **Jira Server/Data Center:** legacy wiki markup `!filename|thumbnail!`, appended to the plain-string comment/description body, resolved by filename. No ID mapping needed.
- **Jira Cloud — corrected mid-build via real experimentation, not assumed:** initial research (citing Atlassian's own open [JRACLOUD-96383](https://jira.atlassian.com/browse/JRACLOUD-96383) plus explicit community guidance against relying on it) concluded inline thumbnails were **not** reliably achievable on Cloud, only a plain attachment. **This was wrong, corrected by direct experimentation against a real Cloud instance** (`corenexus`, ticket `CNV1-24`): uploading via the classic endpoint, then doing a manual-redirect `GET` on the returned `content` URL, yields a `Location: https://api.media.atlassian.com/file/{UUID}/binary?token=...` — the UUID is the real Media Services `id` the ADF `media` node needs. The community-reported "ID mapping problem" is real (the classic attachment id and this UUID are different ID spaces), but the *resolution* (this exact redirect trick) works. Further surprise: the `media` node's `collection` attribute — which every source treated as needing to be a real, discoverable value — **does not need to be one**; the content-scoped JWT embedded in the resolved UUID is what actually grants read access, and Jira renders a real inline thumbnail given *any* string in `collection` (verified with the ticket's own key, an empty string, and a guessed value — all three rendered correctly, confirmed visually via browser screenshot). `resolveMediaId` failures are swallowed, not surfaced as errors — the classic attachment above already succeeded and is genuinely visible on the issue either way.
- **Linear:** `fileUpload` mutation → presigned PUT → `![filename](assetUrl)` Markdown, rendered inline automatically. No ID-mapping problem at all. Real bug caught before ship: `fileUpload` is workspace-scoped, not issue-scoped — on `ticket_create`, the uploaded asset was completely orphaned from the issue unless its Markdown was folded into the description via a follow-up `updateFields` call, which the initial implementation omitted (caught by `code-reviewer`, fixed with a Linear-only follow-up edit, best-effort — a failure to link is reported, never treated as a failed create).
- **GitHub:** confirmed genuinely unsupported — no PAT-compatible public API exists for uploading issue/comment assets (the only upload endpoint requires a browser session cookie). Refused before the adapter is ever called, same pattern as `ticket_update`'s GitHub-priority refusal.

**Security-reviewer findings, fixed before ship:** this is the first tool in the codebase reading an arbitrary local filesystem path from an AI-invoked MCP tool call — a new exfiltration surface not present in any prior write (comment/transition/assign/link/update/create are all narrow string/enum fields). Explicit user decision: no path allowlist, trust the caller (human or the AI harness they're directing) — same trust boundary as every other free-text field, with size/count/aggregate-byte caps as the only guardrails. Audit-log gap fixed: both `ticket_create` and `ticket_comment` now log the full attempted local path (`attachPaths`) alongside the filename that actually landed (`attachedFilenames`), so a partial failure or a rejected path is forensically reconstructable after the fact — the original implementation logged nothing for `create` and only the sanitized filename (never the real path) for `comment`.

**Code-reviewer findings, fixed before ship:** (1) Linear `ticket_create` asset-orphaning bug above. (2) A successful upload's summary was dropped from the output when the subsequent comment/create write failed afterward — fixed so a caller can never blindly re-upload already-landed files on retry. (3) Linear's presigned PUT URL got only a string-level HTTPS/hostname check, inconsistent with this codebase's DNS-rebind-guard standard for every other server-supplied URL — fixed to reuse `validateResolvedHost` and refuse a 3xx on the PUT, mirroring `guardedFetch`.

Real-instance verification: end-to-end against `corenexus` (Jira Cloud) — `ticket_create` with 4 real `.webp` attachments (upload → round-tripped via the pre-existing `attachment-downloader.mjs` read path, sizes matched), and `ticket_comment` with a real inline thumbnail, confirmed by browser screenshot. 2808 CLI tests (up from a 2578 baseline, purely additive), 0 CRITICAL, 0 HIGH from either review pass.

## Local project/type cache for `ticket_create` — shipped (2026-07-30/31)

10-iteration proposal/refutation loop run before any code, per the user's explicit request. Every previously-uncertain API mechanic verified against a **primary source directly**, not guessed:

- **Jira issue-type discovery:** the original backlog note's own candidate endpoint (`GET /issue/createmeta?projectKeys=X&expand=...`) is confirmed **`"deprecated": true`** in Atlassian's own OpenAPI v3 spec (downloaded and parsed with `node`, not read via the JS-rendered docs UI which `WebFetch` cannot see). - **Linear team listing:** `Query.teams(filter: TeamFilter, first: Int): TeamConnection!` and `Team{id: ID!, key: String!, name: String!}` confirmed directly from Linear's own official generated schema (same `packages/sdk/src/schema.graphql` download used for `ticket_create` itself) — an unfiltered `teams(first: 250)` call lists every accessible team.
- **Cache conventions:** mirrored `brief-cache.mjs` exactly (read directly, not assumed) — per-profile path under `~/.ticketlens/cache/`, path-traversal guard, TTL-checked-on-read with auto-delete-on-expiry, non-fatal write. New file: `ticket-metadata-cache.mjs`. TTL: 24h.

**Design, resolved during the loop:**
- **Reactive-only population** — refined mid-loop from an initial "populate on first success" idea. The cache only ever populates when `runTicketCreate` catches a project- or issuetype-shaped failure (Jira: real `err.details.errors.{project,issuetype}` keys; Linear: a new `err.code = 'PROJECT_NOT_FOUND'` marker on the adapter's existing team-not-found throw, not message-sniffed). Zero cost on the success path, where this data is never used.
- **Never auto-retries the write** — only enriches the failure message with real, current options. Silently substituting a corrected project/type the user didn't type would be a worse failure mode than a clear error (same principle already established for `ticket_create`'s own "never auto-retry a timeout" design).
- **GitHub excluded entirely** — `createTicket` ignores project/type, so this error shape can never occur there.

**Real bug caught via live-instance verification, not by unit tests alone:** the initial cache-hit check was all-or-nothing ("cache exists at all → skip refresh entirely"). A cache populated by an earlier *project*-shaped error has `projects` but no issue types yet for any project; a later *issuetype*-shaped error on the same profile silently got no enrichment because the (incomplete) cache was treated as sufficient. Reproduced live against the corenexus instance: `ticketlens create --project=CNV1 --type=BadType ...` printed no "Known issue types" line even though `listIssueTypes('CNV1')` worked correctly in isolation. Fixed by computing `needsProjects`/`needsIssueTypes` independently and merging into the existing cache rather than replacing it — verified both by a new regression test and by re-running the exact failing live command, which then correctly printed `Known issue types for CNV1: Epic, Subtask, Task, Story, Feature, Request, Bug.`
